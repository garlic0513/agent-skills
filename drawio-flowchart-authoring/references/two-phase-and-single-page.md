# 先全展开后提子流程 · 单页自适应字号

> 从 SKILL.md 下沉（2026-10-28 瘦身重构）。原属 garlic-drawio-flowchart-authoring。

用户原话：**"先不要考虑子流程，先把每个流程图的所有的完整的节点画出来，没问题后再考虑提取共同的子流程出来"**

```
阶段① 展开版（逻辑确认用）：子流程全部内联，一页看到全部节点，不出现调用框
阶段② 定稿版（交付用）    ：按公司标准模板提取公共子流程 + 双线框调用
→ 两版并存、各司其职；展开版别丢掉（推演/对逻辑/培训时更好用）
```

⭐ **"调用子流程"永远不冲突，冲突来自"同一动作画了两遍"** —— 三条判定：

| 冲突类型 | 表现 | 处理 |
|---|---|---|
| **重复定义**（最严重） | 主流程自己画了一套收货，与公共收货子流程并存 | 一份定义原则：要么改成调用，要么在流程说明里声明"不复用 + 理由" |
| **语义重叠** | 主流程已有"交接检查"，子流程里又有"初检" | 加一句边界：交接检查=数量外观；初检=标签/温度/文件 |
| **口径不一致** | 子流程有复核员确认，同类主流程没有 | 控制强度必须对齐（补节点或补说明），否则审计问"凭什么是两套" |

**不复用也要写理由**（成品有监管码/托绑定、退料/退货无 ASN 且退回原库位）：
在图注或《子流程调用关系表》里列「主流程｜调用哪些子流程｜是否复用公共收货｜不复用原因」，
评审看到"想过且有理由"，而不是"每页画得不一样"。

⭐ **阶段② 提子流程时，按【执行顺序】排 + 一次编好号**（用户会直接要"把各个子流程按顺序排一下"）：

```
① 入库链执行顺序：初检(S4) → 收货(S1) → ├扫托(S1.1) ├扫箱(S1.2) └按单(S1.3)
                                        → 超收短收处置(S1.4) → 取消收货(S1.5) → 质检(S3) → 上架(S2)
② 编号沿用已有的 S1–S4【不要重排】，新子流程挂到父级下做二级号（S1.4/S1.5）
   ⚠️ 按执行顺序调整的是"章节/图册顺序"，不是"编号"——重排编号会让蓝图交叉引用全断
③ 每张主流程表要写清"调用哪些子流程"，不调用的写【不复用 + 理由】（见上一节）
④ 蓝图章节按执行顺序排（3.2.1 初检 → 3.2.2 收货(含三个分支) → 3.2.3 超收短收 → 3.2.4 取消收货 → 3.2.5 质检 → 3.2.6 上架）
   → 读者从头读到尾就是一条货从到厂到上架的完整路径，不用来回翻
```

⭐ **空页先行**（用户："先把空白页面建立在那边，重命名一下标明是何流程即可，先不要画流程图"）：
先建 `0 图例与绘制规则` + N 个命名空页（如 `1 原材料采购入库（某制药客户·展开版）`），
**页序与页名先定死** → 后续逐页填内容时 pg id 不用重映射（见 §十三·补 坑②），
交付节奏也变成"一页一页出、每页认可后继续"，返工面最小。

展开后单页节点数常在 30–38，A3（1654×1169）放不下默认行距 → 用公式算，别手调：

```python
avail = H - top - bottom                 # 例 1169-118-26 = 1025
pitch = min(46, avail / (max_row + 1))   # 行距（节点中心距）
node_h = max(26, pitch - 6)
fs = round(min(10, max(7.5, pitch * 0.24)), 1)   # 字号随行距缩，7.5 是下限
dia_h = max(30, pitch - 2)               # 菱形压扁，别撑破行距
```

实测（同一天两条流程）：

| 节点数 | pitch | 字号 | 结论 |
|:-:|:-:|:-:|---|
| 35 | 33.1 | **7.9pt** | 可读，打印 A3 需距屏幕 40cm |
| 38 | 31.1 | **7.5pt** | 到极限 |
| ≥40 | — | <7.5pt | ❌ 别硬塞，拆两张 A3 或改 A3 双倍高 |

⭐⭐ **2026-10-26 又实测一轮（40 节点 × 6 泳道）：调参数救不回来，是数学问题**

```
实测：40 节点 / 6 泳道（车间·收货员·复核员·经理·QC·QA）/ A3 1654×1169
→ pitch 29.3、node_h 21.3、字号 7.2pt ⇒ 收货员泳道仍然糊（35/40/50/55/65/70/75/80 排太密）
根因（可算，不用试）：可用高 ≈1050px ÷ 37 行 = 28px/行；
  中文标签普遍 14–18 字 ⇒ 必然 2 行 = 20px 文字 + 8px 间隙 = 28px，正好卡死
⇒ 【泳道数 ≥6 时，可读节点上限 ≈ 34】；超过就必须三选一，并主动告诉用户"这是数学极限"：
   ① 减节点（合并冗余步，代价=粒度变粗）
   ② 减泳道（⚠️ QA/QC、执行/复核 不能合，会被审计挑）
   ③ 拆两页（唯一不损失信息的解）
```

**压到极限时三个必做前提（缺一个就白调）：**

```
① 行号必须【自动压缩】：删/合并节点后 max_row 没降 → pitch 不变 → 字号不涨，白改一晚
     rows = sorted({n[2] for n in nodes}); rmap = {r:i for i,r in enumerate(rows)}
     nodes = [(n[0], n[1], rmap[n[2]]) + tuple(n[3:]) for n in nodes]
② 同泳道上下元素高度必须 ≤ pitch−8，否则菱形与下一行矩形【相切】（实测 dia_h=pitch-1 → 全页粘连）
     node_h = max(17, pitch-8);  dia_h = max(20, pitch-8)
③ 字号别硬编码 6pt：fs = clamp(pitch*0.245, 6, 10)
   —— 硬编码会让"压到 34 节点后字号该变 7.8 却还是 6"的机会白白浪费
```

⚠️ f-string 里别写三元表达式：`f'...verticalAlign={'top' if pitch<34 else 'middle'}...'`
   → `SyntaxError: f-string: expecting '}'`（本次踩到，整份生成器起不来）
   ⭐ 先算变量 `valign = 'top' if pitch < 34 else 'middle'` 再嵌。

⭐ **单个模块可例外提子流程**（2026-10-26 用户：\"先把超收短收做成一个子流程吧\"）：
展开版某一段分支太多（超收短收要有 登记差异→隔离→采购确认→经理审批→三路处置），
硬塞主流程会把主页面挤爆 ⇒ 单独出一页子流程（13 节点，字号回到 10pt，非常清楚），
主流程里只放【双线调用框】+ 注明页号；并在图例页加一条规则：
「例外：跨部门异常处置（如超收短收）可单独做成子流程页，主流程放双线调用框并注明页号。」
→ 这类"展开版里的局部子流程"是允许的，不违反两阶段法（§十·⑩）。

⭐⭐ **用户 2026-10-26 最终拍板：一律一页，允许字号小到 6pt**（他原话\"一律一页，可以更小pt\"）。
→ 我之前建议\"≥36 节点拆两页\"被**否决**，别再拿这个去问他，也别自己拆页。
→ 超过 40 节点时**主动提示\"已到物理极限\"**并给出选择，但默认仍按一页画。

**压到 6pt 时必做的四个排版修正（不做就是压字）**：

```
① 判定菱形文字 verticalAlign=top —— 否则射线下尖正好压住文字
② 是/否标签【不要挂在线上】：移到菱形右侧
   <mxGeometry x="0.5" y="0" relative="1"><mxPoint x="66" y="0" as="offset"/></mxGeometry>
   （行距 30px 时放线上必压菱形；移到右侧是本轮最有效的一招）
③ 长回退线标签靠【源端】：x="0.14" + y=-7
   （否则会漂到中间某个节点上——本次「单据错·填理由」一度压在 45 节点上）
④ WMS 黄标签贴【节点右侧外侧】(x+w+3)，行距 30px 时贴上方必压上一节点
⑤ 分支节点别靠横向偏移错开（泳道 306/节点 199 时只有 ±50px 余量，+52 反而重叠）
   → 换到【空闲行】或【相邻泳道】（判断错误环节留复核员泳道、更正交回收货员泳道）
```

紧凑布局下必须跟着改的三处：

```
① 系统小标签（WMS/ERP）→ 贴节点【右侧外侧】(x+w+2)，不要再贴右上角 —— 行距 33px 时
   右上角一定压住上一行的框或自己的第一行字
② 结束/拒收节点 → 放进【对应泳道内的下一行】，不要放泳道区外右侧
   （放外面 = 一条横线穿过全部泳道，图立刻变乱）
③ 长文字节点 → 加宽到 150 仍放不下时优先【改文案】("（采购确认）"→"（采购）"），
   而不是继续缩字号
```

### A. 流程图是【业务为中心】，不是【产品为中心】

用户会直接反问：*"流程图是从产品角度设计的文档，流程还是以产品为中心进行动作编排的。我这么理解有问题吗"*
→ **有问题，方向要调**：业务为中心，产品只做约束。

| | 业务为中心（正确） | 产品为中心（错） |
|---|---|---|
| 主语 | 人（采购员/收货员/第二人/QA） | 系统（界面/菜单/按钮） |
| 动作 | 业务动作（核对/扫码/判定/搬运/放行） | 交互动作（点击/填入/提交） |
| 例 | 「收货员扫箱码，系统带出批次」 | 「在条码输入框录入箱码」 |
| 系统 | 只做**小标签**（WMS / WMS-RF / ERP） | 写成节点本身 |

⭐ 一秒判据：**把系统名、菜单名删掉，这句话还成立吗？** 成立=业务 ✓ / 不成立=功能 ✗
⭐ 用户说对的部分要肯定：流程确实受**产品能力约束** → 正解是「业务动作为中心，产品能力为约束，
产品模块另出一张《节点↔模块对照表》」；三种图别混（业务流程图 / 产品功能流 / 接口数据流）。
⚠️ 以产品为中心会断链：客户说"我们不这么干"、QA 问不出控制点、URS→蓝图→OQ 对不上、换系统图就废。

### B. RF 端（手持终端/PDA）怎么体现 —— RF 不是节点，是标签

```
① 首选：节点贴【RF 或 WMS-RF】系统小标签 + 白底（人动手扫码）
② 图太密时：写进节点文字前缀「65 RF扫箱码归组到实物托盘」
③ 图例写一句：RF＝手持终端扫码作业，动作在收货现场/库位现场，不在电脑前
④ 同一条流程内统一用 ①或②
```
三个错误：独立节点 ✗ ｜同一节点贴 WMS+RF 两个标签（重复，RF 就是 WMS 移动端）✗ ｜RF 用蓝底 ✗
（蓝=系统自动；扫码是人做的）。
⭐ 分工口径：**电脑前做 → WMS 白底；现场扫码 → WMS-RF 白底；不用系统 → 灰底。**

### C. 配色三问答（用户会指着图逐个问）

```
Q 蓝底代表什么？        A 这个动作由【系统】做（矩形=系统自动执行 / 菱形=系统判断）
Q 为什么这个不能是蓝？  A 蓝 ≠ "跟系统有关"，而是"系统自己会做"。人点/录/打印/审核 → 白底
Q 泳道标题条也浅蓝？    A 那是泳道底色（部门/岗位），不代表系统操作 —— 最容易混的一处
```
⚠️ **打印 / 上传 / 下载 类节点：无论白底蓝底都要加右下角浅粉单据标签**（最易漏，评审一眼看出）。
