# 业务为中心的画法约定（文档为唯一依据 / 以客户草稿为模板）

> 从 SKILL.md 下沉（2026-10-28 瘦身重构）。原属 garlic-drawio-flowchart-authoring。

### ⭐⭐ 铁律：图的依据是【文档里的流程说明原文】，不是你的想象

用户投诉过：*"你按照蓝图里面的描述进行流程图绘制啊，我看了一下图画的有问题，
比如采购入库流程图的『供应商实物到货』归到了采购部门这个泳道"* ——
即：我自己臆造了一套结构，泳道归属、节点划分全凭\"业务常识\"，没读文档。

```
蓝图 / URS / SOW 里通常有每张图的【流程说明】（编号 1、2、3… 带 8.1.1 这类子步骤）——
⭐ 它才是画图的唯一依据，不是"你觉得业务应该怎么走"。

正确顺序：
① ⭐ 先抠出该流程的「内容概述 + 流程说明」整段原文（含全部子步骤与编号），
   存成 txt 备查（本次提取蓝图 4.1–4.22 共 1000+ 行）
② 节点 = 原文的步骤，⭐ 节点文案带原步骤号（"8.1.1 校验供应商"、"9.2 是否称重"）
③ ⭐ 泳道 = 原文每步的【操作角色】
   原文"供应商将采购货物送到仓库" → 进【供应商】泳道（不是采购部门！）
   原文"采购人员审核 ASN 单"     → 进【采购人员】泳道
④ ⭐ 沿用文档原有的编号体系（本次蓝图是 4.1–4.22，就不要自己重编成 4.1–4.18）
   —— 图号与文档章节号必须能互相引用
⑤ 原文与客户现状冲突的（如原文"ERP 推送采购订单"但 ERP 不打通）→
   ⭐ 仍画出该节点 + 加⚠️注释说明替代做法，不要默默删掉
   （删了客户看不出\"差异在哪\"，也没法在会上确认）
```

⭐ 自查：随机抽 3 个节点，回原文能不能对上下步骤号？对不上 = 画错了。
⭐ 文档的「涉及系统」「批号规则」「货主代号」这类字段也常带范本残留 —— 一并校（见 §十 ⑤）。

### 通用约定

```
· 泳道维度按【系统 / 角色】：如 ERP、WMS-WEB、WMS-RF、WCS、线下动作
· 节点编号与需求文档（URS/SOW）条款对齐，便于核对覆盖率
· 判断节点写清条件来源（例："是否称重 → 查物料主数据是否称重字段"）
· 子流程用"XX流程（子流程）"占位，另图展开
· 画完必做【需求条款对照表】：逐条查流程图是否覆盖（找缺漏 + 需求分歧）
```

---

用户会自己先用亿图画一版草稿（.eddx）发来，然后说"**暂时先当模板，画 XX 流程**"。
正确处理顺序：

```
① ⭐ 先解析他发来的 .eddx（§一），把他那版的泳道名、节点命名风格、
   编号习惯、判断分支写法全部读出来 —— 这才是"模板"的真身，不是你上一版的 .drawio
② 新图沿用他的：泳道维度与名称、节点文案风格（"N.RF：xxx" 这种带角色前缀的写法）、
   判定节点的措辞（"是否需称重""是否符合收货"）、规则批注的写法
③ 只改【业务差异】那一层，逐条列出差异表给他看（例：第一泳道 采购部门→生产车间；
   起点 采购订单→车间完工通知；删掉不适用的"供应商管理判断"）
④ 差异里凡涉及业务取舍的（要不要称重 / 要不要让步收货 / 要不要供应商判断），
   ⭐ 一律写成"待开会确认"的清单，不要自己拍板（他说过"定稿需要双方开会决定"）
```

这套做法的价值：新图看起来和他那版是**同一个人的手笔**，他拿去开会不用重画风格；
而你只花力气在该动的地方。

⭐ 反过来也要检查：从**别的项目/公司模板**抄来时，模板会把上个客户的设备带进来
（本次：模板带 `WCS 泳道 + 是否 AGV 送货`，但客户 URS 里 AGV/WCS 关键词 count = 0）
→ 交付前用"关键词计数法"过一遍设备类泳道，多出来的整列删掉。
